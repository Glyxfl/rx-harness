# rx-harness

面向零售门店数据的 Agent 运行壳与评测闭环。零第三方依赖，纯标准库实现，单机可复现。

## 概览

rx-harness 是一个最小化的 text-to-SQL Agent 运行框架，附带一套可复现的评测流程。项目关注的是让"这次改动是否让 Agent 变好"成为一个可验证的量，自然语言取数只是承载它的场景。

选这个方向的原因是：取数类 Agent 的风险主要不在 SQL 生成，而在结果不可核验。同一个业务问题，答案错时通常没有任何信号；调整 prompt、补充字段说明或加护栏之后，也没有基线可比对。因此项目的重心放在评测侧，包括：

- 60 条分层任务集，答案由 gold SQL 现算，按四种失败模式分层
- 判定器输出对错之外的失败归因标签（12 类，互斥）
- 针对判定器自身的变异测试
- 一组不需要模型凭证即可运行的工程属性实测
- 自进化层：dev/holdout 划分 + 归因驱动补丁 + 修改面白名单，用来验证"从失败中学习"能否成立

任务集分四层，每层针对一种不同的失败原因：

| 层 | 条数 | 测什么 | 典型失败方式 |
| --- | --- | --- | --- |
| L1 单表聚合 | 15 | 能不能把问题翻译成 SQL | 列名猜错、过滤条件漏写 |
| L2 多表 join | 16 | 会不会对齐粒度和 join 键 | join 缺月份条件导致重复计数 |
| L3 口径陷阱 | 16 | 分母、区间、规格是否取对 | 区间对比当全量求和、日均分母用 30 |
| L4 需澄清 | 13 | 知道什么时候不该答 | 硬猜一个数字交上去 |

L4 是刻意加的一层。前三层的问题，补足 schema 和口径基本就能解决；L4 缺的是**用户意图**，写多少字段说明都没用——唯一正确的动作是先问一句。项目为此加了第三种动作 `clarify`，判定器也相应多了三个归因标签。

范围限定在单 Agent、只读 SQL、合成数据。多 Agent 编排、写操作、真实生产库均不在本项目中。

## 设计取舍

只保留能被量化验证的部分。

| 能力层 | 实现位置 | 取舍 |
| --- | --- | --- |
| 执行器 | `harness/loop.py` | 保留单 Agent 的 think→act→observe；不实现多 Agent 编排与断点恢复 |
| 轨迹 | `harness/types.py` 的 `Trace` | 保留，失败归因依赖逐步轨迹 |
| 工具 | `harness/registry.py`、`tools/sql.py` | 声明式注册加统一错误包装；不实现 MCP、异步、并行 |
| 领域知识 | `harness/skills.py`、`skills/` | 用 `SKILL.md` 注入字段定义与业务口径 |
| 安全边界 | `tools/sql.py` 静态 SQL 校验 | 只读数据场景下以 SELECT 校验、表白名单、禁多语句替代容器沙箱 |
| 评测 | `bench/grader.py` | 不做公开基准总分，只做业务标量对错、澄清形态判定加归因标签 |
| 自进化 | `evolve/` | 只在 `skills/` 上做贪心搜索，接受与否只看 dev；补丁形态由人给定，算子不会自己涌现 |

## 目录结构

```
harness/    类型定义、工具注册、skill 加载、主循环、策略
tools/      只读 SQL 工具与静态校验
skills/     四个 SKILL.md：schema、销量口径、排名口径、库存口径
data/       合成业务库生成器（sqlite，随机种子固定）
bench/      任务集、判定与归因、执行器、报告生成、工程属性实测
evolve/     自进化：dev/holdout 划分、失败诊断、补丁、只在 dev 上决定接受
cli.py      build / eval / coverage / evolve / ask
```

链路总览（三种出口各自去向）：

```
question
  └─ skill 注入（schema + 业务口径）
       └─ policy.decide() ──► 三种出口
            ├─ ToolCall(sql) ──► 静态校验（只读 / 表白名单 / 禁多语句）
            │                      └─ sqlite（mode=ro）
            │                           └─ Observation ──► 回到 decide()
            ├─ Clarify(question) ──► 提前终止，判定「是否问到关键缺口」
            └─ Answer(value)     ──► 判定「标量是否正确」
                                      全程记录 Trace，由 grader 归因
```

## 一次问答的内部过程

`ask` 与 `eval` 走同一条链路，差别只落在第 6 步。下面以「城东一店 2026 年 9 月降压片 20mg 卖了多少盒」为例，逐步说明每一环实际在做什么、对应的代码在哪。

**1｜入口。** `cli.py`。`ask` 把用户输入包成一条临时任务（`id=adhoc`、`max_steps=6`）；`eval` 从 `bench/tasks.jsonl` 逐条取任务，每题生成一份独立 `Trace`。两者的任务结构一致，所以调试时的行为就是评测时的行为。

**2｜拼上下文。** 这一步决定后面所有事。`context_prefix()` 读取 `skills/*/SKILL.md`，把表结构（5 张表、字段名与类型）和业务口径（销量按 `qty` 求和即盒数）拼成一段文本，前置到问题之前；`registry.describe()` 再把工具签名渲染成 `sql(sql) -> 执行只读查询`。模型收到的不是用户那句话，而是「说明书 + 工具清单 + 问题」。

这一层是实测中收益最大的一层：同样的模型，注入内容从无到有，60 条任务集的通过数从 11 升到 58（见 B 节）。

**3｜模型决策。** `OpenAICompatPolicy.decide()` 发一次请求，`_parse()` 把返回的 JSON 解析为 `Decision`，只允许三种出口：

| 出口 | 模型输出 | 后续动作 |
| --- | --- | --- |
| 调用工具 | `{"tool":"sql","args":{"sql":"SELECT ..."}}` | 进入第 4 步，循环继续 |
| 直接作答 | `{"answer":"答案：383"}` | 进入第 6 步，`stop_reason=answered` |
| 反问澄清 | `{"clarify":"请问是 20mg 还是 40mg？"}` | 立即终止，`stop_reason=clarified` |

在 `loop.py` 中，澄清的判断排在作答之前——能问就先问，不猜。这是 L4 那层任务的实现基础；没有这个出口，含糊问题只能以「给一个数」收场。

**4｜静态校验。** `tools/sql.py:check_sql()` 五条硬规则：必须以 `SELECT`/`WITH` 开头、不得含 `;`（禁多语句）、不得含注释符、不得含写操作关键字（`insert`/`update`/`drop`/`attach`/`pragma` 等）、`FROM`/`JOIN` 后的表名必须在 `{stores, products, sales, inventory, targets}` 内。通过后连接 `file:...?mode=ro`，连接层本身也是只读。

校验失败不抛异常，而是返回一条 `Observation(ok=False, meta={"error":"unsafe_sql"})`，模型能看到「被拒了、原因是什么」。这一点很关键：如果直接抛异常，模型没有机会换个写法，失败也无法被归因。同理，`sqlite3.Error` 会被收敛成 `tool_error` 而不是中断整轮——早期版本正是让它直接抛出，导致该归因一直是死代码。

**5｜观测回填。** 结果（列名 + 最多 200 行）序列化后写回上下文，连同完整历史再请求一次模型。这里有两个硬预算：步数 6、token 6000。用尽即停，`stop_reason` 记为 `step_budget_exceeded` 或 `token_budget_exceeded`。第 3 至 5 步构成循环，也就是 ReAct 的 think → act → observe。

**6｜收尾。** 两条岔路：

- `ask`：逐步打印 thought、SQL、执行结果，供人工观察，不评分。
- `eval`：`grader.grade()` 用该题的 gold SQL 现算标准值，与 `answer` 末行「答案：」之后的值比对，并给出 12 类归因标签之一。判定支持 strict / lax 两种口径（见 A 节）。

## 为什么要逐步留痕

留痕不是为了日志好看，是为了**失败能被定位到具体一步**。同一个「答错」，可能是第 3 步没想出来（`answered_wrong`）、第 4 步被拦下（`unsafe_sql`）、第 5 步看错结果，或者第 2 步根本没给对信息（`tool_error` 里大量是列名猜错）。没有逐步 `Trace`，这些情况在指标上都只是「错」，无法给出处理方向，也就无法驱动 `evolve/` 那层的补丁生成。

同样地，`0/14` 与 `14/14` 的差别来自第 2 步注入的内容；`8/14 造成数据损坏` 来自拆掉第 4 步后跑同一批 SQL。评测的所有结论都可以回到这条链路上的某一步。

## 快速开始

要求 Python 3.10 及以上，无第三方依赖。

```bash
python cli.py build       # 生成合成业务库 data/rx.db
python cli.py eval        # oracle 校准 + heuristic 基线 + 判定器变异测试
python cli.py coverage    # 工程属性实测，不需要 API key
python -m unittest discover -s tests -v
```

接入真实模型通过环境变量配置（`DEEPSEEK_API_KEY`、`OPENAI_API_KEY`、`RX_LLM_API_KEY` 任选其一）：

```bash
export DEEPSEEK_API_KEY=sk-xxx          # Windows cmd: set DEEPSEEK_API_KEY=sk-xxx
python cli.py eval --provider openai --ablate --repeat 3
```

兼容任意 OpenAI 协议端点：

```bash
python cli.py eval --provider openai --base-url http://127.0.0.1:11434/v1 --model qwen2.5:7b
```

缺少凭证时 `eval --provider openai` 会输出配置提示并以返回码 2 退出，不会静默返回 401。

凭证不入库。环境变量是唯一入口；`tests/test_no_secrets.py` 在每次测试时扫描仓库，命中 `sk-` 开头的密钥、GitHub token 或私钥块即判定失败。

## 评测设计

未经校验的判定器不可信，因此评测分三层，每一层用于排除上一层的失效可能。

**第一层：oracle 校准。** 将 gold SQL 直接传入 harness，结果必须 60/60（L4 的 13 条由 `ClarifyPolicy` 给出问句）。若未全通过，说明链路存在缺陷（校验误杀、取值错误、判定错误），而非模型能力问题。

**第二层：heuristic 基线。** 一个按关键词拼接 SQL 的朴素实现，刻意保留五类常见业务错误：同品名多规格只取第一个、join 目标表漏加月份条件、排行榜缺 `GROUP BY`、库存判断忽略阈值、区间对比当作全量求和。它代表不施加任何领域约束时的水平。

**第三层：判定器变异测试。** 对同一道题注入六类已知故障（错过滤、错聚合、错表、危险 SQL、不给答案、超步数），检查判定器能否归因到对应标签。归因准确率是判定器可信度的下限证明；归因错位会使后续所有调优建立在错误信号上。

## 实验结果

环境：Windows 11、Python 3.10.11、`deepseek-chat`、temperature=0。原始运行记录见 [`reports/`](reports/)。

> **口径说明**：任务集后来由 14 条扩至 60 条并分层，运行壳也在同一时期增加了"缺信息先反问"这一动作。A、B、D 三组是 14 条任务集、**加反问规则之前**的数据，保留原样；B2、C、E、F 已在 60 条任务集上重跑。扩表和加规则都会改变绝对值，两组数字不可直接相比。

### A. 判定口径：strict 与 lax

裸模型（不给 schema、不给业务口径）在两种判定口径下的结果：

| 判定口径 | 通过 | 说明 |
| --- | --- | --- |
| strict | 0/14 | 过程中出现越权 SQL 或工具异常即整题失败 |
| lax | 10/14 (71.4%) | 仅比对最终答案，无答案时回退到过程归因 |

两种口径的差值为 10 题，成因分布于两类，且没有一题是因为算出错误数字：

- 6 题为越权探测。模型先尝试获取表结构（`SELECT name FROM sqlite_master`、套用 PostgreSQL/MySQL 的 `information_schema.columns`），被校验拒绝，归因为 `unsafe_sql`。这 6 题最终都写出了正确 SQL 并给出正确答案。
- 4 题为步数耗尽。模型在猜列名（`sale_date`、`stock_date`、`stock_qty`）时消耗完 6 步预算，未进入作答阶段。

因此 0/14 的主要成因是信息供给不足：模型会先行探测表结构，而越权探测的代价是整题作废。这组对照同时量化了安全边界对成功率的实际影响：

```bash
python cli.py eval --provider openai --ablate --repeat 1 --report-name model-deepseek-full
python cli.py eval --provider openai --ablate --repeat 1 --lax --report-name model-deepseek-lax
```

**60 条任务集上重测时，这个 +10 的差值没有复现，只有 +2**（strict 11/60、lax 13/60）。差异来源是运行壳后来加入了"缺信息先反问"规则：模型被校验拦截后，行为从"硬着头皮答"变成了"转去问用户"，而反问在 L1~L3 的任务上同样判错（`over_clarified`）。也就是说，旧的 +10 里有一部分是行为配置的产物，不是纯粹的护栏代价。这条属于口径变更的交互效应，写在这里，避免被读成"护栏成本很低"。

### B. 注入消融

同一模型、同一任务集，仅改变注入内容，采用 strict 判定：

| # | 注入内容 | 通过 | 成功率 | 平均工具步数 | 平均 token |
| --- | --- | --- | --- | --- | --- |
| 1 | 无 | 0/14 | 0.0% | 4.57 | 577 |
| 2 | 仅业务口径 SKILL（三个口径文档，无 schema） | 11/14 | 78.6% | 1.64 | 291 |
| 3 | 仅字段定义（字段名与类型，无口径注释） | 14/14 | 100% | 1.79 | 295 |
| 4 | schema（字段旁附口径注释）加业务口径 | 14/14（重复 3 次） | 100% | 1.36 | 246 |

2×2 因子对照：

| | 无 schema | 有 schema |
| --- | --- | --- |
| 无业务口径 | 0/14 | 14/14 |
| 有业务口径 | 11/14 | 14/14 |

由此得到两点：

1. 瓶颈在信息供给，不在推理能力。仅提供字段清单（第 3 行），通过率即从 0 升至 14/14。字段名确定后，`GROUP BY`、多表 `JOIN`、除零处理、小数保留均由模型自行完成。
2. 口径文档的边际收益在 schema 到位后归零。无 schema 时它提升 11 题，主要作用是减少表名猜测；schema 到位后增益为 0。原因与信息位置有关：口径写在字段旁时会在生成 SQL 时被直接使用，独立成文档则在读完上下文后即被稀释。

第 2 行的 3 道失败题归因均为 schema 类问题（1 次越权探测、2 次列名猜测报错），口径理解类错误为 0。

### B2. 60 条任务集上的真实模型复测

14 条时三档配置全部满分，任务集已饱和。扩到 60 条后用同一模型复测：

| 配置 | 通过 | 成功率 | 平均工具步数 | 主要归因 |
| --- | --- | --- | --- | --- |
| 无注入（strict） | 11/60 | 18.3% | 1.02 | `unsafe_sql` 43、`over_clarified` 4、`clarify_off_target` 2 |
| 无注入（lax） | 13/60 | 21.7% | 0.97 | `over_clarified` 45、`clarify_off_target` 2 |
| schema + 业务口径 | 58/60 | 96.7% | 1.00 | `over_clarified` 1、`answered_wrong` 1 |

三点变化：

1. **不再饱和。** 注入到位后仍有两题不过，且都是 14 条任务集覆盖不到的失败形态：`q20` 把片区取值写成"城西区"，查询返回空后转去反问；`q26` 在两处并列最低库存的门店间选错。
2. **无注入时的失败结构变了。** 14 条上是"猜列名耗尽 6 步预算"，60 条上是 43 题在第一步查系统表被拦，平均步数 1.02——被拦一次后它不再反复试，直接作答或反问。
3. **方向不变，幅度不同。** 信息注入把通过率从 11/60 拉到 58/60；14 条口径下的 0 → 14 属于同一现象在饱和题型上的极端表现。
4. **L4 对真实模型几乎没有区分度。** 无注入 11/13、注入后 13/13，两处失败均为 `clarify_off_target`（问了，但没问在关键缺口上）。这一层的区分度只对朴素实现成立（0/13）。真实模型天然倾向于在含糊问题前先问一句，所以"会不会问"不是难点，"问得准不准"才是；而后者正是当前关键词判定最粗的地方。

```bash
python cli.py eval --provider openai --ablate --report-name model-60        # 注入开/关
python cli.py eval --provider openai --no-skill --lax --report-name model-60-lax
```

### C. 本地基线（无需凭证）

| 配置 | 结果 | 说明 |
| --- | --- | --- |
| oracle（链路上限） | 60/60 | 链路无缺陷，四层任务全部可判 |
| heuristic（朴素基线） | 9/60 (15.00%) | 38 题 `answered_wrong`、13 题 `needs_clarification_unmet`，无链路噪音 |
| 判定器变异测试 | 6/6 | 六类注入故障均被正确归因 |

分层看朴素实现的表现，能看出任务集确实在不同维度上有区分度：

| 层 | 通过 | 说明 |
| --- | --- | --- |
| L1 单表聚合 | 7/15 | 最直白的求和、排序能拼对 |
| L2 多表 join | 0/16 | 关键词拼接拼不出 join，全部算错 |
| L3 口径陷阱 | 2/16 | 只有两个不需要口径判断的排名题蒙对 |
| L4 需澄清 | 0/13 | 全部硬答，一次也没问 |

L4 的失败明细值得单独看。朴素实现在 13 道题上给出的"答案"是：

| 题目 | 它给的答案 | 实际含义 |
| --- | --- | --- |
| `q60` 销售额多少？ | 12710 | 两个月的**销量**合计，连指标都错了 |
| `q52` 卖得最好的是哪个？ | 12710 | 同上 |
| `q54` 对比一下两个门店的销量 | 12710 | 同上 |
| `q50` 库存还够吗？ | 1573 | 库存合计，答非所问 |
| `q51` 9 月完成率怎么样？ | 18.7574 | 一个拼出来的完成率 |
| `q48` 降压片这个月卖了多少？ | 3170 | 规格合并后的数，且月份可疑 |

在 L4 的 13 道题里，`12710` 出现了 6 次，因为它就是 `SELECT SUM(qty) FROM sales`——一条不需要任何条件的全表求和。

这组数据的意义不在"朴素实现很弱"，而在它揭示了 L4 的真实失效机制：**当模型不知道该答什么、又被要求必须给一个数时，它会抓一个手边最容易算出来的数字交上去**。这类答案看起来完全正常，格式正确、数字真实，只有对照题意才能发现它根本不回答问题。如果没有 L4 这一层，这种失败在评测里是不可见的。

heuristic 的 38 个 `answered_wrong` 对应五类业务错误，示例：

| 任务 | 问题 | gold | 朴素实现 | 错因 |
| --- | --- | --- | --- | --- |
| `q06` | 城南三店 降压片 40mg 库存 | 139 | 119 | 按品名匹配，取到 20mg 规格 |
| `q08` | 城东一店 降压片 20mg 目标完成率 | 1.0881 | 1.363 | join 目标表漏加月份条件，两个月目标行叠加 |
| `q13` | 9 月合计销量最高的一天 | 2026-09-04 | 2026-08-26 | 缺月份过滤，混入 8 月数据 |

### D. 跨模型对照

同样的任务与配置，换成思考模型 `deepseek-reasoner`：

| 模型 | 注入 | strict | lax | 平均工具步数 | 平均 token（本地估） |
| --- | --- | --- | --- | --- | --- |
| `deepseek-chat` | 无 | 0/14 | 10/14 (71.4%) | 4.57 | 577 |
| `deepseek-reasoner` | 无 | 0/14 | 11/14 (78.6%) | 4.14 | 501 |
| `deepseek-chat` | schema + 口径 | 14/14 | 14/14 | 1.36 | 246 |
| `deepseek-reasoner` | schema + 口径 | 14/14 | 14/14 | 1.21 | 238 |

三点结论：

1. 换成思考模型后 strict 仍是 0/14。能力有提升（lax +1 题、步数下降 9%），但失败结构没有变化；越权探测甚至更多（12 次 vs 7~9 次），因为思考模型更倾向于先确认结构再作答。
2. `q01` 的典型轨迹：查 `sqlite_master` 被拒 → `SELECT * FROM sales LIMIT 1` → 逐表看样例 → 推出字段 → 写对 SQL，答案 383 正确。它靠采样自行补回了被拦截的信息，代价是 5 步和一次整题作废。
3. 因此提升模型能力无法替代约束层，也无法替代 schema 注入。两者作用在不同维度：模型能力决定"想不想得到"，信息供给决定"猜不猜得中"，约束层决定"能不能做"。

成本方面，本地 `estimate_tokens` 只统计可见输出，不含 `reasoning_content`，跨模型不可直接比较。实测 4 道题（无注入）的真实计费用量：

| 模型 | prompt | completion | 合计 | completion 倍率 |
| --- | --- | --- | --- | --- |
| `deepseek-chat` | 7773 | 1307 | 9080 | 1.00× |
| `deepseek-reasoner` | 8377 | 2935 | 11312 | 2.25× |

合计 token 约为 1.25 倍，其中 completion 部分为 2.25 倍（推理内容计入 completion）。以本任务的量级，绝对成本差异可以忽略；但在高频调用场景下，思考模型的成本优势需要靠更少的重试与更少的步数来抵消。

### E. 工程属性实测

这些属性无法由模型能力推断，单独实现为可复跑命令。全部在临时副本上执行，不修改主库。

| 组 | 测量对象 | 结果 |
| --- | --- | --- |
| G1 只读校验 | 14 类越权 SQL 是否被拒 | 14/14 被拒，执行后数据指纹完好 14/14 |
| G1 误报面 | 全部 47 条 gold SQL 是否被误杀 | 47/47 放行，误杀 0 |
| G2 破坏性对照 | 移除校验后同一批 SQL 的后果 | 可执行 11/14，造成真实损害 8/14 |
| G3 预算与白名单 | 步数预算、token 预算、未注册工具、工具异常 | 4/4 按预期终止并正确归因 |
| G4 答案提取 | 14 种自然语言包装是否被静默取错 | 静默取错 4 降至 0，契约类 5/5 |
| G5 判定等价性 | 14 组等价写法是否仍判对 | 14/14 判对，数值 14/14 一致 |

其中两项结果需要说明。

**G2 用于验证校验层确实生效。** 同一批 SQL 移除校验后执行：`DROP TABLE` 删除表、`UPDATE sales SET qty=0` 修改数据（行数不变，仅统计行数会漏判）、`SELECT ... FROM sqlite_master` 读取库结构。另外 3 条（`comment`、`attach`、`pragma`）未造成即时损害，但提供了写入或挂载能力，此类风险只能靠入口静态拦截。

**G4 是实测过程中发现的自身缺陷。** 修改前的判定器取回答中的第一个数字，"2026 年 9 月共 1234 盒"被判为 2026，导致答对被记为答错，会系统性低估模型能力。修复方式为收窄输出契约（answer 末行强制为 `答案：<值>`），并在多个数字缺少标记时归因为 `ambiguous_answer`，不强行取值。代价是精确率下降，收益是不再产生误判。

### F. 自进化（Evolve）

评测解决"改得对不对"，进化解决"能不能自己改"。这一层的目的不是把分数刷上去，而是把"从失败中学习"这件事做得可验证。

**三条硬约束。** 缺一条，循环就会退化成刷分：

1. 60 条题按 (level, expect) 分层切成 dev / holdout 各 30，划分冻结在 `bench/splits.json`。**接受与否只看 dev**，holdout 每代都跑但只记录。
2. 可改面白名单只有 `skills/`。题目、判定器、任务集都不开放。
3. 每代前存快照，未提升即回滚；报告逐条列出补丁及其证据来源。
4. 接受度量默认用**通过题数**而不是准确率，避免"分母变小"被算成进步。这一条与 2 有重叠，但作用独立——见下表最后两行。

**学习者。** `evolve/learner.py` 的 `KnowledgeGatePolicy` 不是大模型，是一个**只有"知识缺口"这一个缺陷**的确定性策略：文档里写过表名、列名、值域、规格对应关系，它就写对；没写过，它就和真实模型一样去猜（`date` 猜 `sale_date`、`region='城东'` 猜 `'城东区'`、两个规格混成一个）。这样做的原因写在模块注释里——进化环路是否闭合与学习者是模型还是规则无关，而模型会引入采样噪声，把"环路不通"和"这次没抽到"混在一起。换成真模型只需替换 policy 工厂，接口一致。

**四种补丁，其中两种是反例。**

| 模式 | 动作 | dev | holdout | 泛化差距 |
| --- | --- | --- | --- | --- |
| `rule` | 从失败证据归纳缺失知识，补进文档 | 13 → 20 → 21 → 23 → 30 | 15 → 17 → 20 → 24 → 30 | **0 pp** |
| `memory` | 把失败题的原题与标准 SQL 追加为示例 | 13 → 23 | 15 → 15 | 26.7 pp |
| `cheat`（受白名单约束） | 改评测集：跳过失败题 | 补丁被拒，循环终止 | — | — |
| `cheat`（放开 `bench/`，按准确率接受） | 同上 | 13 → 13/13 = **100%** | 15/30 = 50% | 50 pp |
| `cheat`（放开 `bench/`，按通过题数接受） | 同上 | 13 → 13，判为未提升并回滚 | 15/30 | — |

下面两行是同一件事、两种接受度量，差别只在分母算不算数：

- **按准确率接受**（`--accept-metric rate`，业界最常见的做法）：删掉 17 道难题，分母从 30 变 13，dev 立刻 100%。**挡住它的只有修改面白名单。**
- **按通过题数接受**（`--accept-metric count`，本项目默认）：删题不改变通过数，13 → 13，判为未提升、回滚。修改面白名单之外，接受准则本身也挡住了它。

所以准确的说法是：准确率口径对"分母变小"没有免疫力，必须靠白名单兜底；把度量换成绝对通过题数，等于多一道不依赖白名单的护栏。这一行数字之所以值得留，是因为大多数团队的循环用的是前者。

**`rule` 模式的四代分别修了什么。**

| 代 | 证据 | 补丁 | dev | holdout |
| --- | --- | --- | --- | --- |
| 0 | 9 题报错 `no such column: target` / `area` | 按库结构重建整段字段清单 | 13 → 20 | 15 → 17 |
| 1 | 片区查询返回空 | 补值域映射（`城东` 不是 `城东区`） | 20 → 21 | 17 → 20 |
| 2 | 双规格产品答错 | 补"规格必须显式指定"规则 | 21 → 23 | 20 → 24 |
| 3 | 7 题条件不全却直接给数 | 归纳"缺失维度要先确认"的通用规则 | 23 → 30 | 24 → 30 |

第三代补丁值得单独说明：它**没有读** `task["clarify_keywords"]`（那是判定器用的关键词，读了等于抄答案），只从失败形态"没有任何过滤就全表求和"归纳出一条通用规则，然后 dev 的 7 题和 holdout 的 6 题一起修好。

**从人工文档出发也还有缺口。** 不做任何预先挖空，直接以 `skills/` 现有文本为起点：dev 22/30、holdout 21/30。进化用两代补上了两类**文档里从来没写过**的事实——片区取值、以及"缺信息要先确认"这条规则——最终两边都是 30/30。也就是说，13 道 L4 全错的原因不是模型不会问，是文档从没要求它问。

**换成真实模型当学习者。** 上面的数字全部来自可控策略。把 policy 换成 `deepseek-chat`（temperature=0.7，这个温度不是为了效果，是为了让抖动显形），dev 每代重复 3 次：

第一版诊断层在第 0 代就停了：dev 28/30，两处失败是 `q09`（`over_clarified`——文档里写着"表里没有 region 字段"，模型信了，转去问用户"城东区对应哪些门店"）和 `q29`（`answered_wrong`——按门店求完成率，做成了把各月目标加总）。诊断层当时只认"猜错列名 / 片区查询返回空 / 双规格答错 / 该问没问"四类，这两类都不在其中，于是报"无可执行补丁，停止"。

补上 `doc_gap` 分支（本可作答却反问 → 按库结构补全字段清单与取值域，内容全部从库结构现取，不抄标准 SQL）后重跑：

> 第一幕的报告生成于"失败明细"字段加入之前，逐题归因另存在 `reports/verify-llm-raw.txt`（复跑当时留下的初始状态所得）。

| 代 | dev 逐轮（补丁前 → 后） | 中位数 | holdout | 补丁 |
| --- | --- | --- | --- | --- |
| 0 | 27/28/28 → 27/29/29 | 28 → 29 | 27 → 29 | `rule-doc-gap` |
| 1 | 27/29/29 | 29 | 29 | 无可执行补丁（剩 1 题 `answered_wrong`，无对应算子） |

两个必须说明的点：

1. **单次口径会否掉一个真实改进。** 第 0 代按首轮比较是 27 → 27，判"未提升"、应当回滚；按三轮中位数是 28 → 29，接受。报告里的「单次口径与重复口径的分歧」一节自动统计这件事：有补丁可判的 1 个代次里，两种口径结论相反 1 次。
2. **补丁收益小于采样噪声。** 同一份 prompt、同一个模型、同一个知识状态，三轮通过数在 27~29 之间浮动（跨度 2 题，约 6.7 个百分点），而这次补丁的收益是 +1 题。在 30 题的规模上，真实效应比噪声还小——单次比较在这里不是"有点抖"，是**没有信息量**。要么重复测量，要么把任务集做大，没有第三条路。

**这条补丁修的是人工文档的真实缺陷，可以单独验证。** 隔离实验：只在 schema 文档末尾追加一段值域说明（门店名与编号对应、`stores.region` 取值为 `城东`/`城西`/`城南` 且不带"区"字后缀），其他一字不改。q20 在同一温度下 4 次运行由 2/4 通过变为 4/4 通过（原文档的两次失败均归因 `over_clarified`）。人工文档里只有"`region` TEXT，所属片区"，既没列举取值，也没提示这个后缀问题——这条事实是进化补出来的。需要说明的是：这个实验只证明了"这段值域说明"整体有效，没有细分到具体哪一行起了作用。

三种模式可复跑：

```bash
python cli.py evolve --modes rule,memory,cheat                     # 可控学习者，默认先挖缺口
python cli.py evolve --modes rule --no-degrade                     # 从现有文档出发
python cli.py evolve --modes cheat --allow-bench --accept-metric rate   # 演示"删题"奏效
python cli.py evolve --modes cheat --allow-bench --accept-metric count  # 同一作弊被回滚
python cli.py evolve --policy llm --repeats 3 --generations 4       # 真实模型当学习者（需 key）
python cli.py evolve --policy llm --repeats 1                       # 单次口径，对照用
```

`--repeats 1` 与 `--repeats 3` 的差别就是上面第 1 点：接口一样，结论可能相反。

## 局限

1. 60 条任务不构成统计显著性。它的作用是覆盖四种失败模式、把不同配置之间的差距拉出来，不是给出置信区间。四层之间的难度差异明显（朴素基线 7/0/2/0），但同一层内部的题目难度没有量化标定。真实模型已在 60 条上跑过（11/60 → 58/60），但每档只跑一次，没有重复，因此 58 与 60 的差别无法判断是能力还是噪声。
2. L4 的判定依赖关键词命中，这是工程折中。它能挡住"万金油式提问"，但挡不住"命中了关键词却问得很含糊"。要真正评价澄清质量，需要人工标注或第二个模型参与，那又会引入新的不可信环节——当前的取舍是宁可判得粗一点，也不引入一个自己都无法验证的判定源。
3. temperature=0 下"重复 3 次全对"等同于单次运行的确定性，不能作为鲁棒性证据。真正测抖动的是进化实验里的 temperature=0.7：同一状态三轮通过数浮动 2 题（27~29），这个幅度已经超过大多数单条补丁的收益。
4. 只测了两个模型，且同属一家厂商。`deepseek-chat` 与 `deepseek-reasoner` 的差异说明"思考模式不能替代 schema 注入"，但不足以支撑跨厂商的模型能力结论。Claude、GPT、Qwen 等未测。
5. schema 是在查看失败 trace 之后补充的，属于用测试集指导改动，14/14 不代表泛化能力。已做的部分控制是删除 schema 中"列名是 name，不是 store_name"一类定向提示后重跑，结果仍为 14/14，说明起作用的是一般化的字段定义；但顺序偏差无法消除。
6. 单题结论不稳定。早期版本中，按片区查询销量一题曾因 `region` 实际取值为"城东"而模型猜测"城东区"，稳定失败并输出"该片区无门店，销量 0 盒"。更换命名后该失败不再复现，说明它是命名特性而非通用规律。
7. L4 的任务是把真实歧义人工提炼出来的，比真实对话规整。真实用户提问往往同时缺三四个信息，而这里每次只缺一个。多层歧义下的澄清策略（一次问清还是分次问）没有覆盖。
8. 真实模型的进化只跑了 2 代、1 个模型、1 次实验。它证明了环路能接上真模型、且单次口径会否掉真实改进，但不足以给出"真模型能被进化多少"。更要紧的是：真模型与可控学习者的瓶颈不同——可控学习者卡在列名与取值，真模型卡在"信了文档里的一句缺失"。同一套算子对两者的效果不可互相推断。
9. **诊断层的覆盖面就是进化的天花板。** 第一次用真模型跑时，诊断层对 `over_clarified` 没有分支，整个循环在第 0 代以"无可执行补丁"结束——失败看得见，但归纳不出补丁。补上分支才走通两代。现在仍有一类失败（`answered_wrong` 里不属于片区/规格的）只能被记为 `uncovered`，不产生补丁。这不是 bug，是"算子空间由人给定"的直接后果。
10. 补丁由人（本仓库作者）预先定义形态：重建字段清单、补值域、补规格规则、归纳澄清规则、补文档缺口。所谓"自进化"到此为止是**在给定算子空间里做贪心搜索**，算子本身不会涌现。把算子也交给模型生成（这才是 AWorld 所说 Evolve 的完整形态）没有做，因为那需要先解决"生成出来的补丁怎么验证"，而那正是本项目已经建好的那套东西——顺序上应当是先有尺子再有自动改。
11. 单一 seed 的划分、单一学习者、三种补丁形态，都不足以给出"进化的平均收益"。`rule` 模式 5 代收敛、真模型 2 代停在 1 题之差，都只是单次样本。

## 常见问题

**为什么不用容器沙箱？**
威胁模型不同。只读业务数据需要防范误写、越权表与注入，SQL 静态校验可以覆盖；容器沙箱防范的是任意代码执行，本项目不存在该攻击面。代价已在实测 A 中量化：校验会拒绝模型的表结构探测，直接影响成功率。合理的处理方式是显式提供 schema，避免开放系统表查询。

**校验降低了通过率，是否应当移除？**
不应移除。实测 A 显示校验使裸模型从 lax 判定的 10/14 降至 strict 判定的 0/14，但该 10/14 中有 6 题在过程中产生过越权语句。生产环境下一次 `DROP TABLE` 的代价与一次答错不在同一量级。正确做法是补足信息供给，使模型无需越界。

**变异测试是否属于自测？**
其测试对象是判定器，与 Agent 行为无关。归因标签错误会使后续调优建立在错误信号上，因此它提供的是判定器可信度的下限，不构成新的跑分指标。

**归因标签如何划分？**
共 12 种，互斥：`ok`、`answered_wrong`、`ambiguous_answer`、`no_answer`、`no_action`、`step_budget_exceeded`、`token_budget_exceeded`、`unsafe_sql`、`tool_error`、`needs_clarification_unmet`、`over_clarified`、`clarify_off_target`。每个标签对应一种处理方向：`tool_error` 补 schema，`answered_wrong` 补口径，`step_budget_exceeded` 检查列名猜测，`unsafe_sql` 检查其想获取的信息，`needs_clarification_unmet` 检查是否在用"猜"替代"问"。

最后三个标签是随 L4 任务引入的，对应两种相反的错：

- `needs_clarification_unmet`：该问没问，硬给了一个数。这是 L4 最主要的失败方式。
- `over_clarified`：不该问却问了。在信息已经足够的前三层任务上提问，同样算失败——否则模型学会"凡事都先问一句"就能刷分。
- `clarify_off_target`：问了，但没问到关键缺口（比如规格歧义时去问年份）。它防止"随便问一句"蒙混过关。判定方式是按任务的 `clarify_keywords` 做命中检查，而不是看有没有出现问号。

**为什么不按"答案格式"判定 L4？**
问号不是证据。一个万金油式的"请问您想查询什么？"含问号、且对任何题都成立，但它没有降低任何歧义。所以 L4 的判定落在"是否命中该题的关键缺口"上，每个任务在 `tasks.jsonl` 里显式声明缺的是规格、时间、门店、指标口径还是阈值。

**L4 的 oracle 是不是自欺？**
是校准，不是能力。`ClarifyPolicy` 拿到的就是答案（该题缺哪个字段），它只用于证明判定器能识别提问形态并正确归因——和用 gold SQL 校准 oracle 是同一件事。它不代表模型会问，模型表现必须靠实测。

**为什么不直接用 LangChain / DSPy 写？**
分工不同，取舍不同，下面按"换成它会不会更好"逐项判断，而不是笼统地说不用框架。

*Agent 运行时（`harness/loop.py`，约 70 行）*：LangChain 的 `AgentExecutor` 能替代它，附带重试、消息管理、工具 schema 生成。问题在于本项目要跑消融——同一道题、只改注入内容、比较归因分布。框架自己的重试和消息拼装会进入 trace，一旦结果异常，无法区分是模型的行为还是框架的行为。**这里不是 LangChain 更差，是它替我做了决定，而我要看的正是那些决定。**

*判定与归因（`bench/grader.py`）*：LangChain 没有对应物，它不负责"这次失败属于哪一类"。这一层无论如何都得自己写。

*自进化（`evolve/`）*：这一层最该考虑换。若目标是自动优化 prompt，DSPy 的 MIPROv2 一类做法比手写贪心更系统（它会做指令与示例的联合搜索、带 bootstrap 采样）。**本项目的做法是"在给定算子空间里贪心 + 留出集验证"，价值在于把"泛化差距"变成了可观测数字（0 pp vs 26.7 pp），不在于搜索效率。** 若换成 DSPy，这套 dev/holdout 与审计机制仍然需要，因为 DSPy 优化完同样会过拟合 dev。

*权衡结论*：如果目标是尽快做出一个可用的取数 Agent，用 LangChain 更省事，应当换；如果目标是**测量**取数 Agent 的行为并让人相信这个测量，框架会成为不可控变量，不换是对的。两者不冲突——本项目的判定器可以直接拿去评一个 LangChain 写的 Agent。依赖实测（39 个传递依赖）、触发替换的条件、以及未完成的测量，见 [`docs/tooling-decision.md`](docs/tooling-decision.md)。

## 后续计划

1. 把 L4 的关键词判定升级为分级判定：问对关键缺口算满分，问到相关但非关键的点算部分分。真实模型在 L4 上 13/13 通过（无注入也有 11/13），说明"会不会问"已不是难点，剩下的信息全在"问得准不准"里，而这一层现在判得最粗。
2. schema 补充至枚举值、空值语义、单位与取值范围，而非仅字段名与类型。这一条已被进化实验证实有效：只补一段值域说明，q20 就从 2/4 变成 4/4。
3. 把任务集扩到 200 条以上。真模型的补丁收益是 +1 题，而同一状态的采样抖动是 ±1~2 题；在 30 题的规模上做接受决策，信号本来就小于噪声，靠统计方法救不回来，只能靠样本量。
4. 接入其他厂商模型（Claude、GPT、Qwen），补齐跨厂商横向对比。目前只覆盖 DeepSeek 的两个变体。
5. 对比两种元数据访问方式：当前方案为显式注入 schema 并禁用系统表查询；另一种为放行系统表只读并提供 `describe_table` 工具。前者节省 token 但换库需改 prompt，后者更通用。
6. 让算子本身可生成：当前五种补丁形态是人工定义的，下一步是让模型读失败证据自己提补丁，用现有白名单 + 留出集验证是否接受——即"自动提出改动"而不是"自动执行给定改动"。这也是诊断层覆盖面的根本解法：现在每出现一种新失败形态，都要人补一个分支。
