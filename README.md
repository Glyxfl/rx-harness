# rx-harness

> 面向零售门店数据的 **Agent 运行壳 + 评测闭环**。零第三方依赖、纯标准库、单机可完整复现。
>
> 核心不是"做一个能查数的 Agent"，而是**把"Agent 到底行不行"变成一个能被证伪的数字**：
> 先证明评测器本身可信，再用它去量化每一次工程改动的收益。

## 这个项目想解决什么

自然语言取数（text-to-SQL Agent）最难的不是生成 SQL，而是三件事：

1. **错了不知道**。老板问"9 月卖了多少"，Agent 答 1437，没人能当场判断这个数对不对。
2. **不知道错在哪**。是字段猜错了、口径理解错了，还是它压根没查到数据却给了个 0？
3. **改了不知道有没有变好**。改 prompt、加字段说明、加护栏，凭感觉说"好像准了"。

所以这个项目的重心全部压在**评测**上：一套业务口径的任务集、一个能归因的判定器、
一层"对评测器自身做变异测试"的验证，再加一组不需要模型凭证就能跑的工程属性实测。

一句话：**没有评测，就没有优化，只有许愿。**

## 设计取舍

只留能被量化验证的部分，砍掉所有"看起来厉害但讲不清收益"的东西。

| 能力层 | 本项目实现 | 取舍理由 |
| --- | --- | --- |
| 执行器 | `harness/loop.py` | 只留单 agent 的 think→act→observe；不做多 agent 编排与断点恢复 |
| 轨迹 | `harness/types.py` 的 `Trace` | **必须保留**：归因完全依赖轨迹，没有轨迹就没有"为什么错" |
| 工具 | `harness/registry.py` + `tools/sql.py` | 只要声明式注册 + 统一错误包装；不做 MCP、异步、并行 |
| 领域知识 | `harness/skills.py` + `skills/` | 用 `SKILL.md` 注入口径与 schema；投入最小、收益最高的一层 |
| 安全边界 | `tools/sql.py` 的静态 SQL 护栏 | **主要取舍**：只读业务数据不需要容器沙箱，SELECT 校验 + 表白名单 + 禁多语句足够 |
| 评测 | `bench/grader.py` | 不做"公开基准总分"，只做"业务标量对错 + 失败归因标签" |
| 自进化 | 未实现 | 没有稳定评测和足量数据之前，自进化是空中楼阁 |

## 结构

```
harness/    类型、工具注册、skill 加载、主循环、策略
tools/      只读 SQL 工具 + 静态护栏
skills/     四个 SKILL.md：schema / 销量口径 / 排名口径 / 库存口径
data/       合成业务库生成器（sqlite，零外部依赖，随机种子固定）
bench/      任务集、判定与归因、执行器、报告生成、工程属性实测
cli.py      build / eval / coverage / ask
```

一次请求的数据流：

```
question
  └─ skill 注入（schema + 业务口径）
       └─ policy.decide()  ──► ToolCall(sql)
            └─ 护栏校验（只读 / 表白名单 / 禁多语句）
                 └─ sqlite（mode=ro）
                      └─ Observation ──► Trace（逐步落盘）
                           └─ grader：gold 对错 + 归因标签
```

## 快速开始

Python 3.10+，零第三方依赖。

```bash
python cli.py build       # 生成合成业务库 data/rx.db（随机种子固定，随时可重建）
python cli.py eval        # oracle 校准 + heuristic 基线 + 评测器变异测试
python cli.py coverage    # 工程属性实测：护栏 / 预算 / 判定器（不需要 API key）
python -m unittest discover -s tests -v
```

接真实模型只需一个环境变量（`DEEPSEEK_API_KEY` / `OPENAI_API_KEY` / `RX_LLM_API_KEY` 任选其一）：

```bash
export DEEPSEEK_API_KEY=sk-xxx          # Windows cmd: set DEEPSEEK_API_KEY=sk-xxx
python cli.py eval --provider openai --ablate --repeat 3
```

任何 OpenAI 兼容端点都可以（DeepSeek / 通义 / vLLM / Ollama）：

```bash
python cli.py eval --provider openai --base-url http://127.0.0.1:11434/v1 --model qwen2.5:7b
```

没有 key 时 `eval --provider openai` 会直接给出配置提示并以返回码 2 退出，不会静默 401。

> **凭证不会入库。** 环境变量是唯一入口；`tests/test_no_secrets.py` 会在每次跑测试时扫描整个仓库，
> 一旦出现 `sk-...`、GitHub token、私钥块等真实凭证形态就直接失败。

## 评测设计

一个从没被验证过的评测器，本身不可信。所以评测分三层，逐层往上证明。

**第一层 · oracle 校准**
把 gold SQL 直接喂给 harness，它必须 100% 通过。否则说明是链路 bug（护栏误杀、取值错误、判定错误），
不是模型不行。这是"给测试本身做测试"。

**第二层 · heuristic 基线**
一个按关键词拼 SQL 的朴素实现，**刻意保留 5 类团队一开始都会犯的真错**：
同品名多规格只取第一个 / join 目标表忘加月份条件 / 排行榜不 `GROUP BY` /
库存判断忽略阈值 / 区间对比当成全量求和。它才是"不做任何领域约束时的真实水平"。

**第三层 · 评测器变异测试**
对同一道题注入 6 类已知故障（错过滤、错聚合、错表、危险 SQL、不给答案、超步数），
看判定器能否归因到对应标签。**归因准确率 = 评测器可信度的下限证明。**
这一步比跑分重要：归因错了，后面所有优化都是在错误信号上做。

## 实测结果

环境：Windows 11 / Python 3.10 / 模型 `deepseek-chat` / temperature=0 / 14 条任务。
原始报告全部在 [`reports/`](reports/)，每条结论都能用文末命令复现。

### A. 判定口径：严格 vs 宽松（本项目最有信息量的一组）

裸模型（不给 schema、不给口径）在两种判定口径下的成绩：

| 判定口径 | 通过 | 说明 |
| --- | --- | --- |
| **严格**（过程中出现越权 SQL 或工具异常，整题即失败） | **0/14** | 生产口径：真删过表的 Agent，答案再对也不算成功 |
| **宽松**（只看最终答案；没给答案时才回退到过程归因） | **10/14 (71.4%)** | 能力口径：用来区分"不会做"和"会做但越界了" |

差出来的 10 题，成因只有两件事，**没有一道是算出了错误数字**：

- **6 题**越权探测：模型先去找表结构（`SELECT name FROM sqlite_master`、
  套用 PostgreSQL/MySQL 的 `information_schema.columns`），被护栏拒绝 → 判 `unsafe_sql`。
  但这 6 题最后其实都写出了正确 SQL、给出了正确答案。
- **4 题**步数耗尽：撞墙猜列名（`sale_date`、`stock_date`、`stock_qty`）花光 6 步预算，没机会作答。

所以 `0/14` 不等于"模型不会"。**它等于"模型在信息不足的情况下会先越界试探，而越界的代价是整题作废"。**
这条正是安全边界对吞吐的定价，也是本项目最想讲清楚的一件事。

复现（两条命令，对照即得）：

```bash
python cli.py eval --provider openai --ablate --repeat 1 --report-name model-deepseek-full
python cli.py eval --provider openai --ablate --repeat 1 --lax --report-name model-deepseek-lax
```

### B. 注入消融：schema 是决定性变量

同一模型、同一 14 条任务，**只改注入内容**（严格判定）：

| # | 注入内容 | 通过 | 成功率 | 平均工具步数 | 平均 token |
| --- | --- | --- | --- | --- | --- |
| 1 | 无（裸模型） | 0/14 | 0.0% | 4.57 | 577 |
| 2 | 仅业务口径 SKILL（三个口径文档，无 schema） | 11/14 | 78.6% | 1.64 | 291 |
| 3 | 仅纯字段 schema（字段名 + 类型，无任何口径注释） | 14/14 | 100% | 1.79 | 295 |
| 4 | schema（字段旁带口径注释）+ 业务口径 | **14/14（重复 3 次全对）** | **100%** | **1.36** | **246** |

2×2 因子对照：

| | 无 schema | 有 schema |
| --- | --- | --- |
| **无业务口径** | 0/14 | 14/14 |
| **有业务口径** | 11/14 | 14/14 |

两个结论：

1. **瓶颈是信息供给，不是推理能力。** 只给一份字段清单（第 3 行），通过率从 0 直接到 14/14。
   模型拿到字段名之后，`GROUP BY`、多表 `JOIN`、除零、保留小数这些它自己就会。
2. **口径文档的边际价值，在 schema 到位后归零。** 没有 schema 时它有用（0 → 11，
   帮模型少猜几次表名），有了 schema 之后 +0。原因不难理解：**口径要出现在字段旁边才会被用上**，
   写成一份独立文档，模型读完就过去了。

第 2 行那 3 道失败题也佐证了这一点——它们的归因全是 schema 类问题（1 次越权探测、2 次猜错列名报错），
不是口径理解错。

### C. 基线校准（本地，不需要 key）

| 配置 | 结果 | 说明 |
| --- | --- | --- |
| oracle（链路上限） | 14/14 | 链路无 bug |
| heuristic（朴素基线） | **5/14 (35.71%)** | 9 个失败**全部**归因到 `answered_wrong`，无链路噪音 |
| 评测器归因 | **6/6** | 6 类注入故障全部正确识别 |

heuristic 的 9 个失败正好对上 5 类业务坑，举三例（gold → 朴素实现给出）：

| 任务 | 问题 | gold | 朴素实现 | 错因 |
| --- | --- | --- | --- | --- |
| `q06` | 城南三店 降压片 **40mg** 库存 | 139 | 119 | 按品名匹配，取到了 20mg 那个规格 |
| `q08` | 城东一店 降压片 20mg 目标完成率 | 1.0881 | 1.363 | join 目标表没加月份条件，两个月目标行 |
| `q13` | 9 月合计销量最高的一天 | 2026-09-04 | 2026-08-26 | 缺月份过滤，8 月数据混进来了 |

### D. 工程属性实测（`python cli.py coverage`，不需要 key）

模型能力回答不了"约束有没有生效"。所以这几项单独做成可复跑的实测，
全部在临时副本上执行，不依赖任何外部服务、不碰主库：

| 组 | 测什么 | 实测结果 |
| --- | --- | --- |
| G1 只读护栏 | 14 类越权 SQL 是否被拒 | **14/14 被拒**，执行后数据指纹完好 **14/14** |
| G1 误报面 | 14 条 gold SQL 是否被误杀 | **14/14 放行**，误杀率 0 |
| G2 破坏性证明 | 去掉护栏后同一批 SQL 的后果 | 可执行 **11/14**，造成真实损害 **8/14** |
| G3 预算与白名单 | 步数预算、token 预算、未注册工具、工具异常 | **4/4** 按预期终止并正确归因 |
| G4 答案提取 | 14 种自然语言包装是否会被静默取错 | 静默取错 **4 → 0**，契约类 **5/5** |
| G5 判定等价性 | 14 道题换一种写法是否仍判对 | **14/14** 判对，数值 **14/14** 一致 |

两点值得单独说：

- **G2 证明护栏不是摆设。** 同样的 SQL 去掉护栏后，`DROP TABLE` 真的删了表、
  `UPDATE sales SET qty=0` 真的把数据改了（行数不变，只数行会漏判）、
  `SELECT ... FROM sqlite_master` 真的读走了库结构。另外 3 条（`comment`/`attach`/`pragma`）
  没造成即时损害，但它们打开的是**能力**而不是当场出事——这类风险只能靠入口静态拦截。
- **G4 是实测抓出来的自身 bug。** 修改前的判定器直接取回答里第一个数字，
  "2026 年 9 月共 1234 盒"被判成 2026 —— 它把**答对记成了答错**，会系统性低估模型能力。
  修法不是让正则猜得更聪明，而是收窄输出契约（answer 末行强制 `答案：<值>`）
  ＋ 多数字无标记时归因为 `ambiguous_answer` 而不硬猜。代价是精确率略降，换来"绝不冤枉"。

## 这套数字该怎么读（也是局限）

1. **14 条任务区分不了 60% 与 65%。** 它的作用是**发现失败模式**（schema 缺失、步数不足、
   枚举值缺失都是靠它发现的），不是统计显著性。而且现在三个配置都已 14/14，**评测集已饱和、测不出差异**。
2. **temperature=0 下"重复 3 次全对"≈ 跑了一次**，不能当鲁棒性证据。它只说明在这条路径上是确定的。
3. **只测了一个模型。** 单一模型说明不了"模型能力"这个命题，只能说这一家在这个任务集上的表现。
4. **schema 是看过失败 trace 之后才加的**，属于用测试集指导改动，14/14 不能当泛化能力。
   做过的部分控制：把 schema 里"列名是 name，不是 store_name"这类定向提示删掉重跑仍是 14/14，
   说明起作用的是 schema 本身；但"先看失败再加 schema"的顺序偏差无法消除。
5. **单题结论不稳，别当规律。** 早前版本里有一题（按片区查销量）曾因 `region` 枚举值
   实际是"城东"而模型猜成"城东区"，稳定失败并输出"该片区无门店，销量 0 盒"。
   换成本次这套命名后同一坑不再复现——**同一个失败模式换个命名就消失，说明它是命名特性，不是通用规律。**

## 设计权衡 FAQ

**为什么不用容器沙箱？**
威胁模型不同。只读业务数据要防的是"误写、越权表、注入"，SQL 静态校验能覆盖；
容器防的是"任意代码执行"，本项目没有这个攻击面。代价也测出来了：护栏会拒绝模型的表结构探测，
直接影响可用性（见实测 A）——所以正确答案是**显式提供 schema**，而不是给它开一个查系统表的口子。

**护栏拖累了效果，是不是应该关掉？**
不该。数据见实测 A：护栏确实让裸模型从 10/14 掉到 0/14，但那 10/14 里有 6 题在过程中写过越权语句。
在生产里，一次 `DROP TABLE` 的代价和一次答错完全不是一个量级。正确做法是把信息补足（schema 注入），
让模型不需要越界，而不是把护栏拆了。

**变异测试算不算自测？**
它测的不是 agent，是**评测器**。归因标签错了，后面所有调优都是在错误信号上优化。
所以它是可信度的下限证明，不是又一个跑分。

**为什么归因标签只有 8 个？**
够用且互斥：`ok` / `answered_wrong` / `ambiguous_answer` / `no_answer` / `no_action` /
`step_budget_exceeded` / `token_budget_exceeded` / `unsafe_sql` / `tool_error`。
每个标签都直接对应一种改法：`tool_error` → 补 schema；`answered_wrong` → 补口径；
`step_budget_exceeded` → 查是不是在猜列名；`unsafe_sql` → 看它想拿什么信息。

## 下一步

1. **任务集 14 → 60，并做难度分层**（单表聚合 / 多表 join / 口径歧义 / 需要反问澄清的模糊问题）。
   现在 14/14 已经没有区分度——一个测不出差异的评测集等于没有评测。
2. **schema 补到"枚举值 + 空值语义 + 单位 + 取值范围"级别**，而不是只写字段名和类型。
3. **temperature=0.7 跑 N 次的稳定性测试**，现在的"稳定"只是确定性，不是鲁棒性。
4. **接第二家、第三家模型做横向对比**，把"模型能力覆盖"这个命题从单点扩成切面。
5. **元数据访问方式对比**：现在是"显式注入 schema + 禁查系统表"，另一种是
   "放行系统表只读 + 提供 `describe_table` 工具"。前者省 token 但换库要改 prompt，后者更通用。值得跑一组。
