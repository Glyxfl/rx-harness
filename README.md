# rx-harness

面向零售门店数据的 Agent 运行壳与评测闭环。零第三方依赖，纯标准库实现，单机可复现。

## 概览

rx-harness 是一个最小化的 text-to-SQL Agent 运行框架，附带一套可复现的评测流程。项目关注的是让"这次改动是否让 Agent 变好"成为一个可验证的量，自然语言取数只是承载它的场景。

选这个方向的原因是：取数类 Agent 的风险主要不在 SQL 生成，而在结果不可核验。同一个业务问题，答案错时通常没有任何信号；调整 prompt、补充字段说明或加护栏之后，也没有基线可比对。因此项目的重心放在评测侧，包括：

- 14 条业务口径任务集，答案由 gold SQL 现算
- 判定器输出对错之外的失败归因标签
- 针对判定器自身的变异测试
- 一组不需要模型凭证即可运行的工程属性实测

范围限定在单 Agent、只读 SQL、合成数据。多 Agent 编排、写操作、真实生产库均不在本项目中。

## 设计取舍

只保留能被量化验证的部分。

| 能力层 | 实现位置 | 取舍 |
| --- | --- | --- |
| 执行器 | `harness/loop.py` | 保留单 Agent 的 think→act→observe；不实现多 Agent 编排与断点恢复 |
| 轨迹 | `harness/types.py` 的 `Trace` | 保留，失败归因依赖逐步轨迹 |
| 工具 | `harness/registry.py`、`tools/sql.py` | 声明式注册加统一错误包装；不实现 MCP、异步、并行 |
| 领域知识 | `harness/skills.py`、`skills/` | 用 `SKILL.md` 注入字段定义与业务口径 |
| 安全边界 | `tools/sql.py` 静态 SQL 校验 | 只读数据场景下以 SELECT 校验、表白名单、禁多语句替代容器沙箱 |
| 评测 | `bench/grader.py` | 不做公开基准总分，只做业务标量对错加归因标签 |
| 自进化 | 未实现 | 缺少稳定评测与足量样本时无法验证收益 |

## 目录结构

```
harness/    类型定义、工具注册、skill 加载、主循环、策略
tools/      只读 SQL 工具与静态校验
skills/     四个 SKILL.md：schema、销量口径、排名口径、库存口径
data/       合成业务库生成器（sqlite，随机种子固定）
bench/      任务集、判定与归因、执行器、报告生成、工程属性实测
cli.py      build / eval / coverage / ask
```

一次请求的执行路径：

```
question
  └─ skill 注入（schema + 业务口径）
       └─ policy.decide()  ──► ToolCall(sql)
            └─ 静态校验（只读 / 表白名单 / 禁多语句）
                 └─ sqlite（mode=ro）
                      └─ Observation ──► Trace（逐步记录）
                           └─ grader：gold 比对 + 归因标签
```

## 快速开始

要求 Python 3.10 及以上，无第三方依赖。

```bash
python cli.py build       # 生成合成业务库 data/rx.db
python cli.py eval        # oracle 校准 + heuristic 基线 + 判定器变异测试
python cli.py coverage    # 工程属性实测，不需要 API key
python -m unittest discover -s tests -v
```

接入真实模型通过环境变量配置（`DEEPSEEK_API_KEY`、`OPENAI_API_KEY`、`RX_LLM_API_KEY` 任选其一）：

```bash
export DEEPSEEK_API_KEY=sk-xxx          # Windows cmd: set DEEPSEEK_API_KEY=sk-xxx
python cli.py eval --provider openai --ablate --repeat 3
```

兼容任意 OpenAI 协议端点：

```bash
python cli.py eval --provider openai --base-url http://127.0.0.1:11434/v1 --model qwen2.5:7b
```

缺少凭证时 `eval --provider openai` 会输出配置提示并以返回码 2 退出，不会静默返回 401。

凭证不入库。环境变量是唯一入口；`tests/test_no_secrets.py` 在每次测试时扫描仓库，命中 `sk-` 开头的密钥、GitHub token 或私钥块即判定失败。

## 评测设计

未经校验的判定器不可信，因此评测分三层，每一层用于排除上一层的失效可能。

**第一层：oracle 校准。** 将 gold SQL 直接传入 harness，结果必须 14/14。若未全通过，说明链路存在缺陷（校验误杀、取值错误、判定错误），而非模型能力问题。

**第二层：heuristic 基线。** 一个按关键词拼接 SQL 的朴素实现，刻意保留五类常见业务错误：同品名多规格只取第一个、join 目标表漏加月份条件、排行榜缺 `GROUP BY`、库存判断忽略阈值、区间对比当作全量求和。它代表不施加任何领域约束时的水平。

**第三层：判定器变异测试。** 对同一道题注入六类已知故障（错过滤、错聚合、错表、危险 SQL、不给答案、超步数），检查判定器能否归因到对应标签。归因准确率是判定器可信度的下限证明；归因错位会使后续所有调优建立在错误信号上。

## 实验结果

环境：Windows 11、Python 3.10.11、`deepseek-chat`、temperature=0、14 条任务。原始运行记录见 [`reports/`](reports/)。

### A. 判定口径：strict 与 lax

裸模型（不给 schema、不给业务口径）在两种判定口径下的结果：

| 判定口径 | 通过 | 说明 |
| --- | --- | --- |
| strict | 0/14 | 过程中出现越权 SQL 或工具异常即整题失败 |
| lax | 10/14 (71.4%) | 仅比对最终答案，无答案时回退到过程归因 |

两种口径的差值为 10 题，成因分布于两类，且没有一题是因为算出错误数字：

- 6 题为越权探测。模型先尝试获取表结构（`SELECT name FROM sqlite_master`、套用 PostgreSQL/MySQL 的 `information_schema.columns`），被校验拒绝，归因为 `unsafe_sql`。这 6 题最终都写出了正确 SQL 并给出正确答案。
- 4 题为步数耗尽。模型在猜列名（`sale_date`、`stock_date`、`stock_qty`）时消耗完 6 步预算，未进入作答阶段。

因此 0/14 的主要成因是信息供给不足：模型会先行探测表结构，而越权探测的代价是整题作废。这组对照同时量化了安全边界对成功率的实际影响：

```bash
python cli.py eval --provider openai --ablate --repeat 1 --report-name model-deepseek-full
python cli.py eval --provider openai --ablate --repeat 1 --lax --report-name model-deepseek-lax
```

### B. 注入消融

同一模型、同一任务集，仅改变注入内容，采用 strict 判定：

| # | 注入内容 | 通过 | 成功率 | 平均工具步数 | 平均 token |
| --- | --- | --- | --- | --- | --- |
| 1 | 无 | 0/14 | 0.0% | 4.57 | 577 |
| 2 | 仅业务口径 SKILL（三个口径文档，无 schema） | 11/14 | 78.6% | 1.64 | 291 |
| 3 | 仅字段定义（字段名与类型，无口径注释） | 14/14 | 100% | 1.79 | 295 |
| 4 | schema（字段旁附口径注释）加业务口径 | 14/14（重复 3 次） | 100% | 1.36 | 246 |

2×2 因子对照：

| | 无 schema | 有 schema |
| --- | --- | --- |
| 无业务口径 | 0/14 | 14/14 |
| 有业务口径 | 11/14 | 14/14 |

由此得到两点：

1. 瓶颈在信息供给，不在推理能力。仅提供字段清单（第 3 行），通过率即从 0 升至 14/14。字段名确定后，`GROUP BY`、多表 `JOIN`、除零处理、小数保留均由模型自行完成。
2. 口径文档的边际收益在 schema 到位后归零。无 schema 时它提升 11 题，主要作用是减少表名猜测；schema 到位后增益为 0。原因与信息位置有关：口径写在字段旁时会在生成 SQL 时被直接使用，独立成文档则在读完上下文后即被稀释。

第 2 行的 3 道失败题归因均为 schema 类问题（1 次越权探测、2 次列名猜测报错），口径理解类错误为 0。

### C. 本地基线（无需凭证）

| 配置 | 结果 | 说明 |
| --- | --- | --- |
| oracle（链路上限） | 14/14 | 链路无缺陷 |
| heuristic（朴素基线） | 5/14 (35.71%) | 9 个失败全部归因为 `answered_wrong`，无链路噪音 |
| 判定器变异测试 | 6/6 | 六类注入故障均被正确归因 |

heuristic 的 9 个失败对应五类业务错误，示例：

| 任务 | 问题 | gold | 朴素实现 | 错因 |
| --- | --- | --- | --- | --- |
| `q06` | 城南三店 降压片 40mg 库存 | 139 | 119 | 按品名匹配，取到 20mg 规格 |
| `q08` | 城东一店 降压片 20mg 目标完成率 | 1.0881 | 1.363 | join 目标表漏加月份条件，两个月目标行叠加 |
| `q13` | 9 月合计销量最高的一天 | 2026-09-04 | 2026-08-26 | 缺月份过滤，混入 8 月数据 |

### D. 工程属性实测

这些属性无法由模型能力推断，单独实现为可复跑命令。全部在临时副本上执行，不修改主库。

| 组 | 测量对象 | 结果 |
| --- | --- | --- |
| G1 只读校验 | 14 类越权 SQL 是否被拒 | 14/14 被拒，执行后数据指纹完好 14/14 |
| G1 误报面 | 14 条 gold SQL 是否被误杀 | 14/14 放行，误杀 0 |
| G2 破坏性对照 | 移除校验后同一批 SQL 的后果 | 可执行 11/14，造成真实损害 8/14 |
| G3 预算与白名单 | 步数预算、token 预算、未注册工具、工具异常 | 4/4 按预期终止并正确归因 |
| G4 答案提取 | 14 种自然语言包装是否被静默取错 | 静默取错 4 降至 0，契约类 5/5 |
| G5 判定等价性 | 14 道题改写为等价 SQL 是否仍判对 | 14/14 判对，数值 14/14 一致 |

其中两项结果需要说明。

**G2 用于验证校验层确实生效。** 同一批 SQL 移除校验后执行：`DROP TABLE` 删除表、`UPDATE sales SET qty=0` 修改数据（行数不变，仅统计行数会漏判）、`SELECT ... FROM sqlite_master` 读取库结构。另外 3 条（`comment`、`attach`、`pragma`）未造成即时损害，但提供了写入或挂载能力，此类风险只能靠入口静态拦截。

**G4 是实测过程中发现的自身缺陷。** 修改前的判定器取回答中的第一个数字，"2026 年 9 月共 1234 盒"被判为 2026，导致答对被记为答错，会系统性低估模型能力。修复方式为收窄输出契约（answer 末行强制为 `答案：<值>`），并在多个数字缺少标记时归因为 `ambiguous_answer`，不强行取值。代价是精确率下降，收益是不再产生误判。

## 局限

1. 14 条任务不足以区分 60% 与 65%，其作用是发现失败模式（schema 缺失、步数不足、枚举值缺失均由此发现），不构成统计显著性。三个配置现已全部 14/14，任务集饱和，当前版本测不出配置差异。
2. temperature=0 下"重复 3 次全对"等同于单次运行的确定性，不能作为鲁棒性证据。
3. 仅测试一个模型。单一模型的结果不支持"模型能力"层面的结论。
4. schema 是在查看失败 trace 之后补充的，属于用测试集指导改动，14/14 不代表泛化能力。已做的部分控制是删除 schema 中"列名是 name，不是 store_name"一类定向提示后重跑，结果仍为 14/14，说明起作用的是一般化的字段定义；但顺序偏差无法消除。
5. 单题结论不稳定。早期版本中，按片区查询销量一题曾因 `region` 实际取值为"城东"而模型猜测"城东区"，稳定失败并输出"该片区无门店，销量 0 盒"。更换命名后该失败不再复现，说明它是命名特性而非通用规律。

## 常见问题

**为什么不用容器沙箱？**
威胁模型不同。只读业务数据需要防范误写、越权表与注入，SQL 静态校验可以覆盖；容器沙箱防范的是任意代码执行，本项目不存在该攻击面。代价已在实测 A 中量化：校验会拒绝模型的表结构探测，直接影响成功率。合理的处理方式是显式提供 schema，避免开放系统表查询。

**校验降低了通过率，是否应当移除？**
不应移除。实测 A 显示校验使裸模型从 lax 判定的 10/14 降至 strict 判定的 0/14，但该 10/14 中有 6 题在过程中产生过越权语句。生产环境下一次 `DROP TABLE` 的代价与一次答错不在同一量级。正确做法是补足信息供给，使模型无需越界。

**变异测试是否属于自测？**
其测试对象是判定器，与 Agent 行为无关。归因标签错误会使后续调优建立在错误信号上，因此它提供的是判定器可信度的下限，不构成新的跑分指标。

**归因标签如何划分？**
共九种，互斥：`ok`、`answered_wrong`、`ambiguous_answer`、`no_answer`、`no_action`、`step_budget_exceeded`、`token_budget_exceeded`、`unsafe_sql`、`tool_error`。每个标签对应一种处理方向：`tool_error` 补 schema，`answered_wrong` 补口径，`step_budget_exceeded` 检查列名猜测，`unsafe_sql` 检查其想获取的信息。

## 后续计划

1. 任务集由 14 条扩展至 60 条，并按难度分层（单表聚合、多表 join、口径歧义、需反问澄清的模糊问题）。现有任务集已无区分度。
2. schema 补充至枚举值、空值语义、单位与取值范围，而非仅字段名与类型。
3. 使用 temperature=0.7 重复运行，测量稳定性而非确定性。
4. 接入第二、第三个模型做横向对比。
5. 对比两种元数据访问方式：当前方案为显式注入 schema 并禁用系统表查询；另一种为放行系统表只读并提供 `describe_table` 工具。前者节省 token 但换库需改 prompt，后者更通用。
