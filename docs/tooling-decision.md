# 工具选型记录：为什么不用 LangChain

> 结论前置：**在这个项目里不换。但在"做一个能用的取数 Agent"这个目标下，LangChain 是更好的选择，
> 该换就要换。** 两者不矛盾，因为两个目标交付的东西不同。
>
> 状态：依赖数量为实测（2026-10-27）；冷启动与体积**未测完**，本文不引用。

## 1. 先把"更好"定义清楚

"LangChain 效果更好吗"这句话没有单一答案，因为"效果"至少是三个不同的量：

| 量 | 怎么衡量 | LangChain 是否占优 |
| --- | --- | --- |
| 开发成本 | 写一个能跑的 agent 需要多少行、多少依赖 | **是**，明显 |
| 结果质量 | 同一批题、同一模型的通过率 | 不确定，取决于实现；不构成差异 |
| 可测量性 | 能不能归因失败、能不能做注入消融、能不能审计改动 | **否**，它不解决这个问题 |

所以正确的问法不是"哪个框架好"，而是**"我这次要交付的是哪一样"**。

## 2. 逐层判断

本项目分三层：运行时、评测、进化。三层对框架的依赖完全不同。

| 层 | 代码量 | LangChain 能否替代 | 判断依据 |
| --- | --- | --- | --- |
| 运行时 `harness/loop.py` | 约 70 行 | 能，而且更短 | `create_agent` / `AgentExecutor` 自带重试、消息拼装、工具 schema 生成。手写这 70 行的唯一理由是**这些行为本身要被观察**：做注入消融时，同一道题只改 prompt 内容，若框架自行重试或改写消息，trace 里就分不清是模型的行为还是框架的行为 |
| 判定与归因 `bench/` | 约 300 行 | **无对应物** | LangChain 不负责"这次失败属于哪一类"。这一层无论如何都要写 |
| 自进化 `evolve/` | 约 400 行 | 部分，且**不是最佳选择** | LangChain 本身不含提示词优化。这个位置对口的是 DSPy（指令与示例联合搜索、bootstrap 采样），但 DSPy 优化完同样会过拟合 dev，留出集与审计机制仍然要自己写 |

一句话：**能替代的那一层恰好是我要观察的那一层，不能替代的那两层恰好是项目的全部价值。**

## 3. 实测

| 项 | 本项目 | `langchain`（当前版本） |
| --- | --- | --- |
| 第三方依赖 | 0 | **39 个传递依赖** |
| 数据来源 | 标准库 sqlite3 / urllib | — |

39 个依赖的构成（`pip install --dry-run --report` 实测）：`langchain`、`langchain-core`、
`langgraph`、`langgraph-checkpoint`、`langgraph-prebuilt`、`langgraph-sdk`、`langsmith`、
`pydantic` + `pydantic_core`、`httpx` + `httpcore` + `h11` + `anyio` + `sniffio`、`requests` +
`urllib3` + `certifi` + `charset-normalizer` + `idna`、`orjson`、`ormsgpack`、`xxhash`、`zstandard`、
`tenacity`、`jsonpatch`/`jsonpointer`、`PyYAML`、`typing_extensions`、`websockets` 等。

这不是批评，是代价说明：零依赖换来的"任何人 clone 下来 `python cli.py eval` 就能复现"
是用 39 个依赖换来的。**如果项目的读者只关心结果不关心可复现，这笔交易不划算。**

未完成：冷启动时间、安装体积。本次环境下载超时，未取到数，因此本文不给这两项任何数字。

## 4. 决定

**不换。** 理由是一个可以被检验的句子：本项目的交付物是"一组关于 Agent 行为的可信测量"，
而不是"一个取数助手"。框架会把后者做得更好，同时让前者变得更难。

**换。** 出现下面任一条件时应当换，而不是硬撑：

1. 需要多 provider 快速切换、结构化输出、流式、工具生态（检索、代码执行、MCP）——重写这些不产生任何价值。
2. 需要多 Agent 编排、handoff、持久化状态、人机中断——这是 LangGraph 的领域，手写是浪费。
3. 生产化：可观测性接入（LangSmith）、部署、版本管理。
4. 目标变成"把取数做出来给业务用"，而不是"证明取数做得对不对"。

## 5. 更合理的组合

框架与评测不是二选一。**用 LangChain / LangGraph 写被测 Agent，用本项目的判定器评它**，
是这两件事各自的最优解：

```
LangChain Agent ──► ToolCall / Trace（用 callback 采集）
                        │
                        ▼
              bench/grader.py（本项目的判定与归因）
                        │
                        ▼
                  相同的分数口径
```

这样既能拿到框架的开发效率，又保住了"评测不依赖被测对象"这条底线。本项目当前的
`OpenAICompatPolicy` 与 `KnowledgeGatePolicy` 已经证明 policy 是可插拔的——
再加一个 `LangChainPolicy` 只是实现一个 `decide()`，不需要改判定器。

## 6. 没有做的验证

- **未做同一批题上的 A/B 实现对照**：需要一个能跑真实模型的 key，且只有把判定器与被测对象
  完全解耦后，这个对照才有意义（否则测的是两套判定口径）。
- **未测冷启动与内存**：网络原因，见 §3。

这两项如果补上，"该不该换"就能从判断变成测量。在补上之前，本文的结论只应被当作有依据的判断，
不应被当作测量结果。
