# 模型能力 vs 工程化改造：覆盖评估

> 评估对象：rx-harness 中的 8 项工程化改造。
> 评估问题：**如果去掉某一项，只靠当前主流大模型的能力，能不能拿到同样的结果？**
> 状态：两个轴都已实测（2026-10-26，`deepseek-chat`，temperature=0，14 条任务）。
> - 轴 B（工程属性）：`python cli.py coverage`，本地无需凭证
> - 轴 A（单次正确性）：`python cli.py eval --provider openai`，结果见 §5
> - 实测推翻了我原先的三个判断，修订记录见 §6

## 1. 为什么不能用"成功率"回答这个问题

最直觉的做法是"跑一遍模型，看通过率多少，就知道模型覆盖了多少"。这是错的：

1. **单次通过 ≠ 生产可用。** 模型 10 次对 9 次，通过率 90%，但剩下那次在生产里就是一封发错的报表。
2. **评测本身也是一项被评估的改造。** 用"没有评测的模型"去证明"评测不必要"，是循环论证。
3. **同一个分数可以有完全不同的含义。** 0/14 既可能是"完全不会"，也可能是"全都会做但每次都在过程里越界"。
   这两种情况对应的工程动作完全相反：前者要补信息，后者要收紧边界。

所以下面把评估拆成两个轴，并且**必须用两种判定口径各测一次**。

## 2. 两个轴

| 轴 | 定义 | 谁受模型能力影响 |
| --- | --- | --- |
| **A · 单次正确性** | 给定问题和 schema，模型能否把这道题做对一次 | 强相关。模型越强，轴 A 覆盖越高 |
| **B · 工程属性** | 稳定、可审计、成本可控、有安全边界、可度量 | **无关**。这是运行时约束，不是能力问题 |

大多数"模型强了就不需要工程化"的论断，是拿轴 A 的改善去否定轴 B 的必要性，属于偷换。

## 3. 覆盖率矩阵

| # | 工程化改造 | 解决什么问题 | 轴 A 覆盖（实测） | 轴 B 覆盖 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | Schema 注入 | 让模型知道表/字段/枚举值 | ❌ **不可替代**：裸模型 0/14 → 只给纯字段定义 14/14 | ❌ | **不可替代** |
| 2 | SKILL.md 口径注入 | 私有业务约定（规格歧义、保留位数、并列取法） | ⚠️ 半覆盖：无 schema 时 0→11，有 schema 后 **+0** | ❌ | 半覆盖，且**必须写在字段旁** |
| 3 | 只读 SQL 护栏 | 防误写、越权表、注入 | ❌ 输出空间永远包含写操作（实测：裸模型 6/14 题写过越权语句） | ❌ | **不可替代** |
| 4 | 步数 / token 预算 | 防死循环、控成本 | ❌ 模型没有自我计费能力（实测：4/14 题步数耗尽，且它并未给出错误答案，而是没有机会作答） | ❌ | **不可替代** |
| 5 | Trace 逐步落盘 | 失败可定位 | ❌ 模型输出不是执行轨迹 | ❌ | **不可替代** |
| 6 | 评测集 + 判定 | 知道改好没改好 | ❌ 模型无法自证正确 | ❌ | **不可替代** |
| 7 | 失败归因标签 | 知道**为什么**错 | ⚠️ LLM-as-judge 可辅助，但仍需固定标签体系 | ❌ | 半覆盖 |
| 8 | 最终自然语言回答 | 表达 | ✅ 完全覆盖（措辞都自然，甚至答错时更自然） | ⚠️ 措辞会漂 | 覆盖 |

轴 A 合计：完全覆盖 1 项、半覆盖 2 项、**不可替代 5 项**。
轴 B 合计：**0 项**。

## 4. 轴 B 已实测：`python cli.py coverage`

轴 B 与模型无关，不需要凭证。实测（Python 3.10，全部在临时副本上跑）：

| 组 | 测什么 | 结果 |
| --- | --- | --- |
| G1 只读护栏 | 14 类越权 SQL 是否被拒 | **14/14 被拒**，执行后数据指纹完好 **14/14** |
| G1 误报面 | 14 条 gold SQL 是否被误杀 | **14/14 放行**，误杀率 0 |
| G2 破坏性证明 | 去掉护栏后同一批 SQL 的后果 | 可执行 **11/14**，造成真实损害 **8/14** |
| G3 预算与白名单 | 步数预算、token 预算、未注册工具、工具异常 | **4/4** 按预期终止并正确归因 |
| G4 答案提取 | 14 种自然语言包装是否会被静默取错 | 静默取错 **4 → 0**，契约类 **5/5** |
| G5 判定等价性 | 14 道题换一种写法是否仍判对 | **14/14** 判对，数值 **14/14** 一致 |

三条判断：

**（1）护栏的必要性被量化了。** 去掉护栏后 8 条造成真实损害：`DROP TABLE` 真的删了表、
`UPDATE sales SET qty=0` 真的改了数据、`SELECT ... FROM sqlite_master` 真的读走了库结构。
另外 3 条（`comment`/`attach`/`pragma`）没有即时损害，但打开的是**能力**而非当场出事——
这类风险靠事后检查数据完整性永远发现不了，只能在入口静态拦截。

**（2）度量型改造的价值上升，被一个自身 bug 证实。** 修改前的判定器取回答里第一个数字，
"2026 年 9 月共 1234 盒"被判成 2026，把**答对记成了答错**。这类缺陷不写评测、不做消融就永远发现不了。

**（3）"约束生效"≠"模型无法覆盖轴 B"。** 实测证明的是本实现确实挡住了越权操作；
"模型无法覆盖轴 B"是逻辑论证。前者是工程事实，后者是推理，两者不能混着说。

## 5. 轴 A 已实测：四个注入配置 × 两种判定口径

```bash
export DEEPSEEK_API_KEY=sk-xxx

# 严格判定（默认）：过程中越界即整题失败
python cli.py eval --provider openai --ablate --repeat 3

# 宽松判定：只看最终答案
python cli.py eval --provider openai --ablate --lax

# 分层消融：去掉 schema / 只留 schema
python cli.py eval --provider openai --ablate --exclude-skill schema
python cli.py eval --provider openai --ablate --exclude-skill sales_query \
  --exclude-skill store_rank --exclude-skill reconcile
```

### 5.1 注入消融（严格判定）

| # | 注入内容 | 通过 | 成功率 | 平均步数 | 平均 token |
| --- | --- | --- | --- | --- | --- |
| 1 | 无（裸模型） | 0/14 | 0.0% | 4.57 | 577 |
| 2 | 仅业务口径 SKILL | 11/14 | 78.6% | 1.64 | 291 |
| 3 | 仅纯字段 schema | 14/14 | 100% | 1.79 | 295 |
| 4 | schema + 业务口径 | **14/14（重复 3 次全对）** | **100%** | **1.36** | **246** |

2×2 因子对照：

| | 无 schema | 有 schema |
| --- | --- | --- |
| 无业务口径 | 0/14 | 14/14 |
| 有业务口径 | 11/14 | 14/14 |

### 5.2 判定口径的影响（裸模型，同一批轨迹）

| 判定口径 | 通过 | 失败归因 |
| --- | --- | --- |
| 严格 | **0/14** | `unsafe_sql` 10、`step_budget_exceeded` 4 |
| 宽松 | **10/14 (71.4%)** | `step_budget_exceeded` 4 |

**这是整份评估里最关键的一条。** 差掉的 10 题：

- **6 题**在过程中探测过表结构（`SELECT name FROM sqlite_master`、
  套用 MySQL/PostgreSQL 的 `information_schema.columns`），被护栏拒绝 → 判 `unsafe_sql`。
  **但这 6 题最后都写出了正确 SQL、给出了正确答案**——如果只看答案，它们是对的。
- **4 题**撞步数上限：猜列名（`sale_date` / `stock_date` / `stock_qty`）花光预算，没机会作答。

也就是说：**`0/14` 不等于"模型不会"，它等于"模型在信息不足时会先越界试探，而越界的代价是整题作废"。**

### 5.3 三条发现

**（1）瓶颈是信息供给，不是推理能力。**
只给一份纯字段清单（第 3 行，连口径注释都没有），通过率从 0 直接到 14/14。
模型拿到字段名之后，`GROUP BY`、多表 `JOIN`、除零、保留小数这些它自己就会。

**（2）口径文档的边际价值，在 schema 到位后归零。**
没有 schema 时有明显作用（0 → 11，帮模型少猜几次表名），有了 schema 之后 **+0**。
原因不复杂：**口径写在字段旁边才会被用上**；写成一份独立文档，模型读完就过去了。

**（3）安全边界确实伤害可用性，但正确解法不是拆边界。**
护栏让裸模型从 10/14 掉到 0/14。可那 10 题里有 6 题在过程中写过越权语句——
在生产里，一次 `DROP TABLE` 和一次答错不是一个量级的代价。
正确的解法是把信息补足（显式注入 schema），让模型**不需要**越界，而不是把护栏拆掉。

## 6. 修订记录：实测推翻了三个原判断

| 原判断 | 实测 | 修订 |
| --- | --- | --- |
| "模型覆盖了推理，缺的只是约束" | 裸模型严格 0/14，但宽松 10/14，且 4 题是步数耗尽而非答错 | 推理确实基本覆盖，但**前提是信息供给到位**；Schema 注入从"半覆盖"上调为"不可替代" |
| "SKILL 口径注入是半覆盖，必须保留" | 有 schema 后口径增量 +0 | 口径仍然需要，但**形式要变**：从独立文档挪到字段级注释 |
| "0/14 说明模型做不了这个任务" | 换宽松口径立刻 10/14 | **0/14 是判定口径的产物，不是能力测量结果**。报告任何"通过率"必须同时声明判定口径 |

## 7. 必须承认的局限

1. **14 条任务区分不了 60% 与 65%**，且三个配置已全部 14/14——**评测集饱和、测不出差异**。
   它的作用是发现失败模式，不是统计显著性。
2. **temperature=0**。所谓"重复 3 次全对"在事实上约等于跑了一次，只说明这条路径确定，不能当鲁棒性证据。
3. **只测了一个模型**。单一模型支撑不了"模型能力覆盖"这个命题。
4. **schema 是看过失败 trace 之后才加的**，属于用测试集指导改动，14/14 不能当泛化能力。
   做过的部分控制：把定向提示（"列名是 name 不是 store_name"）删掉后仍 14/14；
   但"先看失败再加 schema"的顺序偏差无法消除。
5. **轴 B 的实测是构造用例**。14 条攻击、14 条包装、14 条等价 SQL 都是手写回归测试，
   覆盖不了真实 LLM 的长尾输出。
6. **单题结论不稳。** 早前版本有一题（按片区查销量）因枚举值"城东"被模型猜成"城东区"而稳定失败，
   输出"该片区无门店，销量 0 盒"——措辞与推理齐全、答案全错。换成本次命名后不再复现。
   同一个失败模式换个命名就消失，说明它是命名特性，不是通用规律。
7. **heuristic 的 35.71% 不是模型能力上限**，那是"按关键词拼 SQL"的水平，与模型无关。

## 8. 一句话结论

**"模型能力强不强"在这个项目上问错了方向。**

实测：给全字段定义，`deepseek-chat` 在 14 道题上做到 100%，平均 1.36 步、246 token；
不给字段定义但在宽松口径下仍有 10/14——它不是不会，是在猜表名、撞护栏、耗步数。
而严格口径下同一批轨迹掉到 0/14。

所以真正的结论是：**模型的推理能力早就够了，卡住它的是信息供给和运行时约束，
这两件事都属于工程改造，不属于模型能力。** 把工程做好，模型立刻能用；把工程省掉，换成任何更强的模型还是 0。

"模型变强了就能省掉工程化"是错的方向：模型越强，对 schema 质量、约束边界、评测精度的要求只会更高。
因为错误会变得更隐蔽——它不会说"我不知道"，它会给你一个措辞完整、推理自洽、数字全错的答案。
